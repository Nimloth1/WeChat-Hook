# 以完成转发链路为目标的工作流程

## 约定的适用范围

用户当前指令决定任务和授权范围。全局指令提供默认做法，项目约定说明本项目的边界；
历史审核文档记录当时的候选及验证，不会把“当时未部署/未发送”变成永久禁止。
用户后来明确要求部署同一诊断补丁，即可推进该补丁，不重新套用之前的临时暂停要求。
新的授权只覆盖对应操作，不连带扩大收件人、消息内容、登录或其他机器的范围。

## 按变化内容决定流程

| 变化 | 默认推进到哪里 | 需要停下来确认的情况 |
| --- | --- | --- |
| 日志、固定错误码、只读诊断 | 最小修改 → 相关验证 → 提交推送 → 在已授权排障环境可逆部署 → 核对生效 | 当前明确禁止部署；诊断本身涉及额外真实发送、私密内存/密钥或账号动作 |
| Python 转发逻辑、已确定范围的故障修复 | 修复直接受影响的调用点，做相关集成回归，按已授予的部署/发送范围继续 | 改变目标、历史消息处理规则、发送次数、失败重试或业务数据语义 |
| 原生 DLL、ABI、对象生命周期、注入/加载或许可边界 | 离线证据与验证，按用户要求独立审核，再在已有或新取得的具体部署授权内上线 | 尚未授权会影响真实微信的操作，或出现新的账号风险 |
| 文档、工作约定、运维记录 | 校验内容、链接和一致性，提交推送 | 不因此运行微信、构建 DLL 或修改生产账本 |

分支推送是代码备份，不等于合并或部署。普通诊断不默认创建 PR；用户明确要审核时才创建。
把相关改动汇成一个可验证批次，避免一个问题拆成数次确认、数个无业务交付的 PR。

## 故障处理

1. 先看实际错误码、两端同一任务的回执、POST/原生进入次数、消费标记和运行状态。明确事实、未知项和影响。
2. 用户已经要求修复/恢复，就直接完成必要的最小修复；同类共用入口一起处理。首次发生但持续阻断业务也应推进恢复。
3. 区分恢复现有服务与新增长期防复发设计。偶发问题先解决本次阻塞，不另造通用恢复框架、永久门禁或额外服务。
4. 错误码缺失时，在现有授权内先补诊断、部署并核对版本，之后取得所需现场证据。离线无法复现就是未复现，不能猜改校验，也不能称作修好。
5. 结论以真实运行结果为准。部署诊断只能说明日志能力已就位，不能说明底层故障解决；暂停未解除也不能称为恢复成功。

已确认未发起发送的任务，可在原账本保留原证据并标为未发送、不重试，再恢复原消费水位。
HTTP/原生结果未知的任务不能按“没发”处理，不能删标记重发。恢复范围必须来自用户的现有指令，
不因“取日志”而悄悄清除暂停或重放失败消息。

## 部署与验证

脚本诊断更新通常只需：停止 PM 运行器、切换经过校验的两端脚本、保持配置范围与账本、重启 PM 运行器，
再检查实际入口版本和健康状态。来宾执行器本来就是按请求启动，不必重开微信。
只有必须更换正在加载的 DLL 时，才由用户正常退出客户端，核对停止后替换并一次打开。

健康探针失败应反映真实暂停，不把探针改绿来掩盖失败。故障恢复后核对账本实际推进和资源回收，
仍不能把原生返回当作送达。写入行为有变化时测一个真实周期，空闲无变化应近零写入。

不要为单次日志修改另建实验平台、全目录备份或重复全套测试。保留足以复核的版本、摘要、结果及一个小回退点。
临时数据在证据保存后清理；大任务遵守全局资源预算和磁盘保留规则。

## 信息分层

- `AGENTS.md`：少量稳定的项目执行规则；`CLAUDE.md` 只指向同一份规则。
- 本文：当前工作流程，不记录不断变化的 PID、许可和任务计数。
- `*-review.md` 与结果 JSON：版本审查证据；只在改到对应实现或核对历史时读取。
- `~/.codex/context/vw12-current.md`：私有机器路径、最近部署事实和未解决阻塞。操作前核对现场，不把历史记录当实时状态。
- `~/.codex/context/archive/`：旧机器事件及事故记录，按需读取。

本次工作约定调整只改变协作流程；不会修改代码中的许可、防重放、暂停、24小时规则或自动转发开关。
