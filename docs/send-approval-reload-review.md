# 发送时读取逐条许可

## 问题与范围

旧版 `RunSendServer` 在创建 controller 时读取一次许可；controller 还将“一次发送已消耗”
视为整个实例的终态。因此即使只是换一条正文，也必须重开微信以重建 controller。
只延长过期时间不能解决这两个问题。

本次修改文字/图片共用的许可读取、许可生命周期、累计资源预算和状态展示，不改原生发送函数、地址、
参数布局、HTTP 绑定、联系人功能或登录。缺失的文件/PDF 发送实现仍不支持。

## 新行为

- 生产 controller 持有读取回调，不在启动时缓存许可。每次 POST 在同一互斥锁内读取
  当前文件，然后校验 token、请求编号、收件人、消息种类、正文/图片摘要和模块摘要。
- 一个请求持久消耗后，替换成另一个明确批准的请求即可继续使用同一 controller、
  HTTP listener 和微信进程，前提是累计资源预算仍足够。新许可本身不会自动发送。
- 旧请求的 `.used-<request_id>` 标记继续使用 `CREATE_NEW`、写通和 flush，在进入私有
  函数前持久化。恢复旧许可或重启程序都不能重新执行已经消耗的请求，不删除旧标记。
- 预检与消耗之间若许可被替换、删除或修改，消耗前再次读取并比较全部字段，拒绝调用。
- 状态接口一次读取一份一致的状态。发送占锁期间不等待原生调用完成，返回
  `SendInProgress=true` 和保守的未配置状态；该字段不表示送达。

旧静态构造接口仅为现有离线测试保留；生产入口明确使用回调构造。

## v1 / v2 文件格式

两者仍要求原来的九个字段，未知字段/版本、畸形内容、无效 token 或摘要均拒绝。

| 版本 | `expires_utc` | 接收人 | 行为 |
| --- | --- | --- | --- |
| 1 | 未来十分钟内的 Unix 秒 | 保留原规则 | 兼容原来短期许可；0 仍非法 |
| 2 | 必须为整数 0 | 只允许数字加 `@chatroom` 的群 ID | 到消耗或撤销为止，不再倒计时 |

v2 不是可任意发送的长期通行证。每条许可仍只能批准一个确定的 request_id、群、种类和
完整内容摘要；下一条不同内容要准备下一份许可，但不需要重开微信。固定业务群由私有
发送配置和每条许可共同绑定，用户的实际群 ID、token 和正文不写进代码或 Git。

删除许可可撤销尚未开始的请求；原生调用开始后不能靠删除文件中止已经执行的操作。
无过期时间意味着一个一直未用、也未撤销的许可会持续有效，因此文件 ACL 和显式撤销
仍是边界，不能称为账号安全保证。许可文件应在同一受保护目录通过临时文件加原子替换
发布；碰到文件忙或不完整读取会拒绝，不自动重试。

发送端继续先持久记录 `.client-attempt-<request_id>`，只发一个 POST，不因超时或返回
未确认而自动重试，并在 finally 中仅撤销自己准备的那份许可。服务端原生预检失败时
尚未写原生消耗标记；客户端尝试标记仍须保留，不得据此重新发送。

## 部署前提与能力判断

新状态增加 `ApprovalReload=per_request`、`ApprovalVersion2GroupOnly=true` 和
`SendInProgress`，旧 Build 名不变。调用方必须观察新能力再使用 v2，不能只依据 Build。
旧 DLL 拒绝 v2；不得绕过保护、热卸载 DLL 或修改正在运行的微信进程来升级。

审核并批准升级 DLL 时仍需一次正常退出/打开使新代码生效；这是版本升级所需，之后换
正文或图片许可本身不再要求重开；累计预算耗尽时会停止发送，安全回收尚未打通，不能承诺长期免重开。此 PR 不部署、不替用户操作该次退出/打开。

## 离线验证

`send_api_tests.cpp` 使用自有进程、临时许可和 fake backend，覆盖：

- 同一 controller 从无许可到第一条中文正文，再到第二条不同中文正文，无重建；
- 保持同一 HTTP listener 的真实 loopback 请求依次批准两条正文；
- 同一实例从文字切换到图片，32 个并发请求和两个 controller 共享持久消耗标记；
- 旧许可恢复和重新创建 controller 后不能重放；静态快照构造的负对照不能接受新正文；
- 删除、畸形文件、关闭许可、旧 token、读取异常，以及预检过程中替换许可；
- v1 的过期保护、v1 的 0 非法、v2 的 0 合法、v2 的非群/非零时间非法；
- 发送占锁时的状态读取不等待该调用，调用结果始终保持 unconfirmed。
